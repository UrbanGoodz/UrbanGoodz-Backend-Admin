## 2. The findings that matter

### 2.1 The driver app's dedicated-routes feature was dead in production 🔴

`DedicatedRouteModel.fromJson` cast `pickup_lat`, `pickup_lng`,
`driver_pay_per_package` and the package counts with `as num?`. PHP serialises
MySQL `DECIMAL` columns as JSON **strings** — the API returns `"29.7604000"` and
`"0.00"`, not numbers — so the cast threw:

```
type 'String' is not a subtype of type 'num?' in type cast
```

The **Assigned Dedicated Routes** screen died before rendering. Because that
screen sits upstream of the manifest, **package scanning was unreachable in
production regardless of the camera.**

It survived review because it only fails when a route actually exists. With none
assigned the screen renders an empty list and looks healthy — which is exactly
what production looked like, since the QA driver had no routes.

**The same pattern was in six more files**, four of them non-nullable casts
(crash on a string *and* on null), all on money fields:

```
driver_job_model.dart   earnings, distance
earnings_model.dart     amount, tips, bonuses, mileage
opportunity_model.dart  reward
payout_model.dart       amount
vehicle_model.dart      year, mileage
earnings_screen.dart    amount, tips
```

Jobs, Earnings, Opportunities and Payouts would each have died the moment those
accounts held data.

**Fixed** by `lib/utils/json_number.dart` (`jsonDouble` / `jsonInt` / `jsonBool`
plus nullable variants), with every API-boundary parse routed through it.
`jsonDoubleOrNull` exists deliberately — collapsing a missing latitude to `0.0`
puts the map pin in the Atlantic, so "absent" and "zero" stay distinct.

**Lesson worth keeping:** a Flutter screen that renders an empty state correctly
tells you nothing about whether it works. Seed data before believing a screen.

### 2.2 Package scanning had no scanner 🔴 → fixed

The manifest screen had an `Icons.qr_code_scanner` button that toggled a text
field hinted `"Enter barcode to simulate scan..."`. There was **no camera or
barcode package in `pubspec.yaml` at all.** Drivers had to read the label and
type it.

Backend was never the problem — `scan-pickup`, `scan-dropoff`, `scan-exception`
and the business-side `/business/packages/scan` all exist and work.

**Now:** `mobile_scanner ^7.1.2`, a real `barcode_scanner_screen.dart`, `CAMERA`
permission (`uses-feature required="false"` so it still installs on a camera-less
device). The decoded value flows into the existing `_handlePackageScan`, so
matching, offline queueing and the endpoints are untouched.

Two deliberate choices:
- **A detection latch.** A barcode sitting in frame fires `onDetect` every frame;
  for a pickup scan that reads as the driver loading the same parcel repeatedly.
- **Manual entry kept** as a secondary action, not deleted. Warehouse labels get
  scuffed and torn, and a driver holding a damaged parcel needs a way through.

**Verified on device:** scanner opens, and `dumpsys media.camera` showed
`Active Camera Clients: (Camera ID: 0, PID: 14158, com.urbangoodz.driver)` —
the app genuinely held and streamed the camera, evicting Google's System
Intelligence service from the other camera.

**NOT verified:** an actual barcode decode. That needs a human to point the phone
at a label. Everything else is in place — see §5.

### 2.3 Stranded responder payouts were bookkeeping only 🔴 → fixed

`releaseEscrow()` set `escrow_status='released'` and wrote a ledger row marked
`completed` while **making no Stripe call**. The money stayed in the platform
balance and someone paid the responder by hand. The ledger asserted the opposite
of the truth, which is the worst property a money system can have.

**Now:** a real `/v1/transfers`, Connect columns on responders, a `pending` state
for responders who cannot yet receive, and `urbangoodz:stranded-payouts-retry`
on a ten-minute schedule to convert pending → paid.

Double-payment is guarded twice: our unique ledger key stops a second row, and
Stripe's `Idempotency-Key` header stops a second **transfer** when a response is
lost in flight rather than never sent.

**Proven end-to-end, not just unit-tested:**

```
transfer_id:  tr_1UEi5ZLrEEOKEy0KyBt4rij3
amount:       12.50 USD
destination:  acct_1HeYbmHqKVQl3R3w
livemode:     false          (Stripe test mode)
VERDICT: PASS
```

Second attempt returned `already_paid` with exactly one ledger row. Reproduce
with `php verify_payout_e2e.php <acct_...>` (untracked, see §6).

Tests: 11 passing, 50 assertions, in `UrbanGoodzStrandedIntegrationTest`.

**One bug the tests caught in my own code:** `payoutResponder` originally asked
"is anything owed?" before "was this already paid?", so a request whose offer
selection changed after payment reported `nothing_owed` and lost the record that
money had gone out. The idempotency check now runs first. Covered by
`test_already_paid_wins_even_when_the_offer_is_unresolvable`.

### 2.5 `.env.local` silently shadows `.env` ⚠️

`AdminPanel_Update_V39/.env.local` exists and is a **full production env file**
(`APP_ENV=production`, `APP_URL=https://admin.urbangoodzdelivery.com`, its own
`APP_KEY`). Because `.env` sets `APP_ENV=local`, Laravel loads `.env.local`
**instead of** `.env`.

Consequences observed this session:
- The admin panel fell back to Laravel's `forge`/`forge` DB defaults and 500'd
- The route optimizer ran on **haversine fallback** because `ORS_API_KEY` lives
  in `.env`, which was never read

**Production is fine** — it has no `.env.local`, and its `.env` carries
`ORS_ENABLED=true` plus a valid key. This is a local-only trap, but it will burn
anyone who tries to reproduce a production behaviour locally.

Workaround used: pass real environment variables, which outrank `.env`:

```bash
DB_DATABASE=urban_goodz_local DB_USERNAME=root APP_ENV=local php artisan ...
```

## 6. Environment gotchas (hard-won, will cost hours to rediscover)

- **`shell_exec` hangs indefinitely in PHP on this machine.** A bare
  `git rev-parse` did not return in 5 minutes. It looks like a slow loop, not a
  hang. `status/build.php` reads `.git` directly instead and runs in 40s. Saved
  as memory `php-shell-exec-hangs`.
- **`adb input text` mangles `!` and `%`.** Use alphanumeric test passwords.
- **Laravel session minting:** `loginUsingId()` calls `session->migrate()`, which
  regenerates the id — read the id *after* `save()`. And since Laravel 9 the
  cookie plaintext is prefixed with an HMAC (`CookieValuePrefix`); without it the
  cookie decrypts and is then discarded as tampered, which looks exactly like
  "not logged in". `AdminMiddleware` additionally requires `is_logged_in=1` and a
  matching `login_remember_token`.
- **The admin login form has a real image captcha** (`custome_recaptcha`).
  Automated admin testing should mint a session, not drive the form.
- **Build times:** vendor APK ~2.5h, driver ~1h on this machine. Use detached
  `nohup` + `Monitor`; backgrounded builds get killed around 10 minutes.
  `PUB_CACHE=C:/pubcache` and `TEMP=C:\javatmp` are mandatory.
- **Playwright:** pin to the version matching the installed browsers (1.62.0
  here) or it demands a 150 MB download.
