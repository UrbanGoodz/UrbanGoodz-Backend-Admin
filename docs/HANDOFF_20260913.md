## 3. Security fixes, in order of severity

**The admin login had a hardcoded bypass.** In the custom-captcha branch, a
failed captcha was caught and then waved through for one pair:

```php
if (captcha does NOT match) {
    if ($input !== '9999' || $email !== 'eaturban2020@gmail.com') {
        return ...'ReCAPTCHA Failed';
    }
    // that pair falls through - failure discarded
}
```

A password was still required, so it was not a way in by itself, but it removed
bot protection from the highest-privilege account and had been live in
committed code. Verified closed against the live site: that exact pair now
returns **ReCAPTCHA Failed** and the session stays signed out.

**A numeric captcha could be answered wrong and still pass.** All public forms
compared with `!=`, and PHP compares two numeric-looking strings as numbers:

```
"123" != "0123"  →  false      "100" != "1e2"  →  false
```

Whenever `CaptchaBuilder` emitted an all-digit phrase, a different string
satisfied it. Not theoretical — the regression test, run against the old code,
posts `0123` against a phrase of `123` and **a contact record is created**.

**With no phrase issued and none typed, `"" != ""` passed.** Posting to
`/vendor/apply` with no captcha at all cleared the gate. Three cases in
`UrbanGoodzPublicSurfaceValidationBoundaryTest` were relying on exactly that to
reach the validator; they now clear it explicitly.

**A solved captcha never expired.** The phrase sat in the session until the
login page was re-rendered, and a script posting straight to the route never
re-renders it — so one solved captcha covered an unlimited run of password
guesses, with only the per-IP limiter (5 in 2 minutes) in the way. Now consumed
on use, across all five forms.

**`config/app.php` read `env('APP_DEBUG', true)`.** Laravel ships that default
as `false`. Production set the key explicitly so it was never exposed, but a
missing key must fail closed. Now does.

Checked and found *not* to be problems: the partial's debug prefill is keyed on
`getEnvMode() == 'dev'`; production runs `APP_MODE=live` and serves `value=""`,
so the answer is not in the page.

Verified end to end: a scan now stores

## 10. Addendum — two blockers found after §9 was written

### 10.1 The driver app cannot build from a clean tree 🔴

`flutter build apk --release` fails on a clean checkout:

```
GeneratedPluginRegistrant.java:44: error: cannot find symbol
  class MobileScannerPlugin
Execution failed for task ':app:compileReleaseJavaWithJavac'
```

No Kotlin compile tasks run at all, so `mobile_scanner`'s Kotlin sources are
never compiled and the generated Java registrant references a class that does
not exist in the output.

It is a three-way toolchain incompatibility under AGP 9.0.1 / Flutter 3.44.6:

| setting | result |
|---|---|
| `android.builtInKotlin=false` (current) | `mobile_scanner` Kotlin never compiles |
| `android.builtInKotlin=true` | `firebase_core` fails — *"'org.jetbrains.kotlin.android' is no longer required since AGP 9.0"* |

`mobile_scanner 7.4.1` applies `kotlin-android` itself only when
`builtInKotlin=false` **and** AGP ≥ 9, which is the current configuration — yet
no Kotlin task appears in the build. `mobile_scanner 7.4.1` is the latest
release, so there is no fixed version to move to. Applying
`org.jetbrains.kotlin.android` at the app module was tried and did not help;
that change was reverted.

**This is pre-existing on `main`, not a consequence of the reconciliation
merge.** `mobile_scanner: ^7.4.0` and `android.builtInKotlin=false` were both on
`main` at `bc156c5` — the commit that bumped the version to *"3.9.2+8 for
release"*. The 3.9.1 APK built earlier in this session succeeded only because
it was an **incremental** build reusing Kotlin artifacts already in `build/`;
after `flutter clean` the same tree fails.

So: no clean machine and no CI runner can currently produce a driver APK, and
the installed 3.9.1 APK on `ZT42268MG6` cannot be reproduced from source.

Most likely fix, untested: upgrade the Firebase plugins to versions that have
dropped their own KGP, then set `android.builtInKotlin=true`. That is a
dependency-upgrade exercise, not a code change.

## 11. Addendum — the §10 blockers are now fixed

### 11.1 Driver app builds from a clean tree again ✅

Root cause was a split between plugins over AGP 9's built-in Kotlin:

- `mobile_scanner 7.4.x` applies `kotlin-android` **only** when
  `android.builtInKotlin=false` - which this project sets - yet no Kotlin task
  ran at all, so its plugin class never existed for the generated registrant.
- Turning built-in Kotlin **on** is not available: eleven other plugins still
  apply KGP unconditionally (`firebase_messaging`, `stripe_android`,
  `camera_android_camerax`, `rive_common`, `thermion_flutter`,
  `speech_to_text`, `device_info_plus`, `share_plus`, `wakelock_plus`,
  `package_info_plus`, `sign_in_with_apple`), and AGP 9 rejects that outright.

Fix: keep `builtInKotlin=false`, pin `mobile_scanner` to **7.0.1**, which
applies KGP like every other plugin here. Pinned exactly, not with a caret -
`^7.1.2` resolves forward to 7.4.1 and reintroduces the failure, which is how
it arrived in the first place. `firebase_core` also upgraded 4.11.0 -> 4.14.0,
which has gained the same conditional guard.

Clean build verified: 78,792,756 bytes, signed with the upload keystore
(cert SHA-1 `a561424324cdaf64691001f70847d599fd76adc0`). Installed on
`ZT42268MG6` as **v3.9.3**, launches with no crash. `main` at `f6d4b38`.

### 11.2 Portal 500s fixed ✅

Eight missing views built and deployed (`8181415`), each from what its
controller actually passes and posting only to routes confirmed in
`route:list`. Seven admin URLs verified 200 as a logged-in admin.

The more valuable find came out of it: the admin layout picks its sidebar with
`@include("layouts.admin.partials._sidebar_{$module_type}")`, and
`$module_type` comes from the request path via `CurrentModule` middleware. A
path it does not recognise - anything under the doubled `admin/admin/urban-goodz`
prefix - leaves it empty, asks for `_sidebar_`, and kills the page on its
**layout** rather than its own content. Now falls back to the default sidebar.

### 11.3 A route the customer app needed did not exist ✅

`OrderAnywhereController::createFromOption` was complete but never routed, so
the customer app was calling an endpoint that did not exist. Registered as
`POST api/v1/order-anywhere/requests/from-option` inside the existing
`auth:api` group, before the `requests/{record}` wildcard. Confirmed on
production with `route:list --path=order-anywhere/requests`.

**Do not probe this from outside to check it.** That group's auth middleware
runs before routing resolves a miss, so an unknown path and a real one both
answer **403**. Before and after the fix, the external response was identical.
The route table is the only ground truth.

### 11.4 Two tooling traps that produced wrong counts

Both cost real time today and will again:

- **`route:list` truncates its action column.** Grepping the text output
  silently misses matches; it made 16 routed views look like 3. Use

- **A regex over controllers matches commented-out and concatenated `view()`
  calls.** `view('admin-views.campaign.' . $type . '.index')` is not a missing
  view. Tokenize and skip a literal followed by `.`.
