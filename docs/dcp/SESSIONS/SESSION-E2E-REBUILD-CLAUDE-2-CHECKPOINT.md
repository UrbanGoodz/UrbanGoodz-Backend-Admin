## What changed after the first review

The review of commit `dc738df` found six issues, all addressed in commit `da79297`:

2. **Personal path fragments remained in the pushed artifact.** The scrub in `dc738df` replaced the literal full path string but missed occurrences where PHPUnit's own output had already truncated the path mid-string, so the exact full-path needle didn't match those instances. `da79297` added a second, regex-based scrub pass and reported zero remaining matches — **that claim was itself wrong; see the second review below.**

Both now assert the exact URL (`route('login', ['tab' => 'admin'])`), matching the same pattern already used and passing in the root-redirect test — verified by reading `AdminMiddleware::handle()` and `Helpers::get_login_url()` to confirm that's genuinely the URL the app produces with no `DataSetting` rows seeded, not assumed.
4. **A stale in-code comment** referenced `test-support/reports/phpunit-feature.txt`, a file that was removed as a stale artifact in the first commit and no longer exists. Corrected to reference `phpunit-full.txt`.
5. **The matrix doc said "10 required fields"** for vendor registration, contradicting the corrected test (14 fields) and this checkpoint. Corrected to 14 throughout.
6. **`RUN_METADATA.md` didn't bind the artifacts to the exact committed source** — added the new test file's SHA-256 and the shell used for the documented commands (Git Bash / POSIX `sh` env-var-prefix syntax, not PowerShell or cmd.exe).

## What changed after the second review

The second review found `da79297`'s "zero remaining matches" claim for item 2 above was itself false: **8 local-path fragments were still present** in the committed `phpunit-full.txt` — 5 inside a truncated `include(...)` stack-trace argument preview, and 3 inside a truncated Passport `CryptKey` constructor argument preview, both cut short by PHP's own string-truncation formatting at a different point than the round-2 scrub anticipated. Root cause, diagnosed directly rather than guessed at: the round-2 scrub regex had its path-separator-character counts hand-derived through three separate escaping layers (shell quoting → PHP double-quoted-string parsing → PCRE parsing), and silently failed to match on these particular truncation shapes; the round-2 *verification* greps had the same blind spot for the same reason, so they falsely reported clean.

Fixed by replacing all of the above with `test-support/reports/verify-no-local-paths.php`, a single checked-in script whose match pattern is built from character-code primitives (`chr(92)` for the path separator) instead of hand-written escape sequences, and which matches the drive-letter/user-profile-directory prefix followed by zero, one, or two trailing separators and anything up to the next quote — so it doesn't need to know where a truncation happened. Before trusting it, it was sanity-checked against a synthetic copy of one of the actual leaked lines to confirm it fails loudly on known-bad input; only then was it run against the real files, which is what actually found and let us close all 8 remaining fragments (plus a dangling truncated remnant left over from the redaction itself). The documentation changes above (this file and `RUN_METADATA.md`) were written only after `php test-support/reports/verify-no-local-paths.php test-support/reports/phpunit-full.txt test-support/reports/new-test-run-3.txt` returned exit 0 against the exact files staged in this commit — not before, and not from memory of what round 2 was supposed to have done.

That remains an open decision for the repository owner, separate from this commit.
